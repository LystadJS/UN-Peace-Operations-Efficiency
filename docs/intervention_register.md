# Normalized intervention register and nonadditivity pools — P06/P07

The [intervention register](../data/portfolio/interventions.json) preserves the nineteen legacy candidate rows, fourteen ranked umbrella rows and nine overlapping mission-child rows, eighteen public opportunities, three transaction cases and eleven arrangement descriptions. Every input has a checksum and its original identifiers and fields remain intact. These are overlapping source populations, rather than independent additional interventions or additive financial exposures.

Fourteen roadmap case scopes use IDs `CASE01`–`CASE14`. Their `roadmap_case_id` values refer to the case-packet work plan; they must not be joined to legacy `candidate_validation.csv` merely because both namespaces use a C prefix. Explicit path/key/value references provide the mapping. For example, CASE02 concerns UNIFIL–UNSCOL assets, links legacy C12/C07 and opportunity P001, and is distinct from the legacy C02 reporting investigation.

The cases cover RSCE charging/workforce, UNIFIL–UNSCOL assets, Haiti aviation/support, UNISFA translation, UNISFA transferred assets, UNSOS fuel recovery, MONUSCO insurance, UNMISS approved post removals, training, joint regional functions, UNOWAS–UNOCA factual support, Cyprus factual support, UNIFIL residual liabilities and existing joint structures. All remain `SCREENING_CANDIDATE`; no state history, financial validation, authenticated cost objects or quantified benefits are asserted. Empty cost-object lists mean that identifiers are needed, rather than that costs are absent. Unknown benefits remain null, rather than zero.

The [twelve benefit pools](../data/portfolio/benefit_pools.json) mark potential shared cost boundaries. Pool names are analytical boundaries, not authenticated ledger cost objects. A unique future recognition key must include the actual cost object, period, counterfactual and benefit category. Alternative interventions on the same underlying cost object are mutually exclusive until separable marginal effects are established. All allocations to one key must total no more than one; an empty allocation ledger presently prohibits benefit recognition.

In particular, CASE02 and CASE13 share the Lebanon transition pool so that an asset purchase alternative cannot be counted without transfer, disposal, residual and security costs. HQ support, training, regional workflows and source preparation also have multiple case memberships. Distinct reporting mandates remain intact; shared input is not proof of duplicated final output. Internal charges and credits eliminate once. Existing reforms, approved post removals and closures belong in the baseline. Recovery, avoidance, capacity and monetary saving categories remain separate under the [cost-accounting standard](cost_accounting_standard.md).

Run `python -B scripts/build_intervention_register.py --write` to regenerate both JSON artifacts and `--check` to verify them. Run `python -B tests/check_intervention_register.py` for corruption checks. These are initial screening-baseline controls: subsequent evidence-backed advancement requires a reviewed model revision and the [candidate advancement](candidate_advancement.md) gates. No monetary aggregate or whole-division savings ceiling is generated.
