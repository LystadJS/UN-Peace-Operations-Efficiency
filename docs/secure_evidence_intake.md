# Restricted evidence intake — E07

**The E01–E06 files are unsent request contracts, not authorization to obtain records.** They specify minimum fields and purposes, proposed custodian roles, record grain and linkage keys. Comparable periods, collection burden, owner acceptance and retention remain unset. Prepare a specific approved request with the competent custodian before collection. No named contact is assigned or contacted by these files.

Use an approved institutional restricted system outside this repository for actual financial, asset, personnel, service and workflow records. Confirm authorized purpose, lawful access, handling classification, permitted analysts, retention and deletion or legal-hold requirements before transfer. An approved role and repository access do not establish permission to view every record.

The custodian should extract only approved fields, assign stable case-specific tokens and retain the re-identification map separately with more restrictive access. Use tokens sufficient to match corrections, partial settlements, one-to-many services and transfers; do not publish tokens, mapping tables or raw extracts. Pseudonymized records can still disclose identities or sensitive operations through linkage and remain restricted. Requests exclude personal names, contact and banking details, diagnoses, precise security movements and unnecessary narrative content. Medical claims work starts with non-identifying control aggregates; claim-level adjudication needs separate institutional authorization.

At intake, retain extraction criteria, source totals, excluded records, correction history, missingness, units, periods, authorized receipt and cryptographic hashes in the approved restricted store. Verify authenticity, source custody and completeness before analytical matching. Record access and derivation history, including rejected or corrected extracts, without copying sensitive metadata into Git. Obtain custodian approval for any non-identifying aggregate or opaque public evidence receipt. Small cells, rare events, free text, geographic detail and linked aggregates require disclosure review; removing names alone is insufficient.

The existing `.gitignore` excludes `data/private/`, `data/restricted/`, `private/`, internal output directories and named export suffixes. Ignored directories are a mistake-containment measure, not approved storage: ignored files can still be copied, force-added or exposed through logs and build artifacts. Keep real extracts outside the checkout. Do not use request JSON, examples, test fixtures, Actions logs or generated reports as an intake channel. If restricted content is staged or exposed, stop publication and invoke the responsible institutional incident procedure; deleting the working file does not erase Git history or previously published copies.

Run `python -B scripts/validate_public_evidence_boundary.py` and `python -B tests/check_public_evidence_boundary.py` before publication. The checker requires purpose-bound field declarations without embedded records or sample values and detects tracked files matching known restricted path patterns. It does not classify arbitrary file contents, scan Git history, prove anonymization, certify infrastructure security or replace substantive disclosure review. Passing it does not authorize sending the requests, collecting data or opening any live-use gate.

E06 retains the existing SP08P1/SP09P1 owner-review and activation controls. Both relevant reporting owners must approve each case separately, approve prospective workload and quality measures, and preserve distinct mandated products and attribution. No live staff records or observation may be collected merely because a template exists; the paused course watch remains paused.
